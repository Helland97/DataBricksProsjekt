# Steg 5: Orkestrering og CI/CD

Goal: run **dlt load → dbt build → tests** as one **Databricks Workflow (Job)** on a schedule. The job takes its code
straight from GitHub (**Git as the source**), so whatever is on the right branch is what runs. Around it, add a
**GitHub Actions** pipeline that checks every pull request: linting, `terraform validate`/`plan`, and `dbt build`
against isolated PR schemas. A PR is merged only when CI is green. The next scheduled run then picks up `main`.

This is the step where the software engineering background pays off: one entry point per task, shared code instead
of copies, pinned versions, idempotent runs, a single required CI check, least-privilege tokens, and cleanup that
can't hit production by mistake.

## 0. Can this step be done without step 4?

**Yes.** Step 4 (access control) was blocked by restrictions in Azure. The blocked parts are the ones that need the
**Databricks account console**: the `databricks.account` provider, account groups, and account-level service
principals (`sp-dbt`, `sp-test-*`). Step 5 needs none of them. It only needs the workspace provider, which already
works, and an identity that CI can log in with (section 2).

| Step 5 part | Needs | From step 4? | Without step 4 |
|---|---|---|---|
| Scheduled job with `git_source` | Workspace provider, warehouse, catalog | No | Works as-is. The `dbt-build` job already uses `git_source` |
| dlt task in the job | Serverless job compute, write to `bronze` | No | Works. The job runs as you, and you own `bronze` |
| `run_as` a service principal | A service principal | **Yes** (`sp-dbt`) | Skip. The job runs as its owner (you). Optional workspace-level SP in section 3.4 |
| Lint, `terraform fmt`/`validate`, `dbt parse` in CI | Nothing (no credentials) | No | Works |
| `terraform plan` in CI | An **Azure** identity (Entra) for the state backend and `azurerm` | No (step 4 didn't plan this) | Tier A only (section 2). Otherwise run `plan` locally |
| `dbt build` on PRs | A **Databricks** identity for CI | No | Tier A, B or C (section 2) |
| Isolated PR schemas | `CREATE SCHEMA` on `lakehouse_dev` | No (step 4 grants are about humans and customers) | Works. You own the catalog. A CI service principal gets the grant from Terraform with the workspace provider |

**What you lose without step 4**, and should say plainly in an interview:
- The job writes as **you**, not as `sp-dbt`. It has all of your privileges, and Delta history shows your user as the
  writer. Without step 4 there is no least-privilege story for the pipeline.
- If CI uses a PAT (tier C), CI has your privileges too. Keep its lifetime short and limit where it can be used
  (section 7.6).
- No row filters or masks. PR builds read unmasked bronze. Since the data is synthetic, that's acceptable here.

**What to do with step 4's leftovers:** `README.md` has an uncommitted section "Tilgangsstyring: roller" that
describes the step 4 roles as if they exist. Either keep it out of the commit (`git restore README.md`) or add one
line on top: *"Planlagt, ikke implementert (blokkert av Azure-begrensninger, se STEG4-PLAN.md)."* Don't commit
documentation that describes infrastructure that doesn't exist. Keep `STEG4-PLAN.md` in the repo: it's a plan you
can talk about.

**Write down what actually blocked step 4** in a short "Kjente begrensninger" section in the README (for example
"not account admin in the Databricks account console" or "not allowed to create app registrations in Entra ID").
Section 2 depends on which one it was.

## 1. What already exists from step 1–3

- `infra/02-databricks/main.tf` has a job **`dbt-build`** with `git_source` (repo `Helland97/DataBricksProsjekt`,
  branch `var.git_branch` = `main`). It has a serverless environment with `dbt-databricks>=1.9,<2.0` and a
  `dbt_task` running `dbt deps` + `dbt build` in `dbt/`, plus a 06:00 Europe/Oslo schedule. It is paused
  (`var.job_schedule_paused = true`). **This step replaces that job with a multi-task job.**
- The repo is **public**, so the job needs no Git credential (`databricks_git_credential` has `count = 0`).
- Ingestion: `ingestion/pipelines/regnskap.py` loads from the **fake API** (`fake_api/app.py`, FastAPI). The API
  serves files from `ingestion/data/`, which is **gitignored** and generated by `generator/generate.py`. The
  generator is **deterministic** (`random.Random(seed)` and `Faker.seed_instance(seed)`, seed 42).
- `ingestion/tests/test_pipeline.py` already starts the fake API with `uvicorn` **in a thread** on a free port and runs

- `pipelines/databricks_setup.py` falls back to `az login` (`DATABRICKS_AUTH_TYPE=azure-cli`) when there is no
  token in `secrets.toml`. **There is no `az` inside a Databricks job**, so this has to change (section 4.3).
- dlt keeps its cursors in `bronze._dlt_pipeline_state` and restores them when the local pipeline folder is empty.
  This is why the job can run on fresh serverless compute every time without losing incremental state.
- dbt: `dbt/pyproject.toml` pins `dbt-core`/`dbt-databricks` `>=1.10,<2.0`, which **doesn't match** the job's
  `>=1.9`. `generate_schema_name` uses `+schema` as-is (`silver`, `gold`, `audit`). Sources point to the `bronze`
  schema by name, and no model hardcodes `lakehouse_dev`, so PR builds can be redirected with one macro (section 7.3).
  `macros/reset_snapshots.sql` hardcodes `schema='silver'` (fix in 7.3).
- Source freshness is configured (`loaded_at_field` from `_dlt_load_id`, `warn_after: 24 hours`).
- `ci/` and `orchestration/` are empty (`.gitkeep`). There is no `.github/` yet.
- Terraform state is in `sttfstatech4821` with **Entra auth** (`use_azuread_auth = true`), and `02-databricks`
  reads `01-azure`'s state. Anything that runs `terraform plan` therefore needs an **Azure** identity.

## 2. Find out which identity CI can get (do this first)

CI needs a non-human identity. Which one you can get depends on what Azure blocked. Try in this order and stop at the
first one that works. **Write the result in the README.**

| Tier | Identity | What it unlocks | Needs |
|---|---|---|---|
| **A** | Entra **app registration** + **GitHub OIDC** (federated credential, no secret) | `terraform plan` **and** `dbt build` in CI | Permission to create app registrations and role assignments in your subscription |
| **B** | **Databricks-managed service principal** created in the *workspace* admin settings + OAuth secret | `dbt build` in CI. No `terraform plan` (no Azure identity) | Workspace admin (you are), and that workspace admins may add service principals |
| **C** | Your **personal access token** (PAT), short lifetime | `dbt build` in CI. No `terraform plan` | Nothing. Always works |

**Why tier A first:** no long-lived secret exists anywhere. GitHub issues a short-lived OIDC token per run, and Entra
trusts it only for this repo and this event. That's the answer interviewers want to hear. An Entra service principal
with **Contributor** on the Databricks workspace resource is **automatically workspace admin** when it logs in via
`azure_workspace_resource_id`, so it doesn't need the account console. That's probably why it works even though step 4
didn't.

### 2.1 Tier A: Entra app + federated credentials (PowerShell)

```powershell
$SUB   = az account show --query id -o tsv
$APP   = az ad app create --display-name "gh-dbxprosjekt-ci" --query appId -o tsv
az ad sp create --id $APP

# One federated credential per event type the workflows use. Subjects are exact matches.
$fc = @{ issuer = "https://token.actions.githubusercontent.com"; audiences = @("api://AzureADTokenExchange") }
az ad app federated-credential create --id $APP --parameters (
  $fc + @{ name = "pull-request"; subject = "repo:Helland97/DataBricksProsjekt:pull_request" } | ConvertTo-Json -Compress)
az ad app federated-credential create --id $APP --parameters (
  $fc + @{ name = "main"; subject = "repo:Helland97/DataBricksProsjekt:ref:refs/heads/main" } | ConvertTo-Json -Compress)
# A job with `environment: ci` (dbt-pr.yml, pr-cleanup.yml) gets the subject "...:environment:ci" instead of
# "...:pull_request". Without this credential, those jobs fail with AADSTS70021 (no matching federated identity).
az ad app federated-credential create --id $APP --parameters (
  $fc + @{ name = "env-ci"; subject = "repo:Helland97/DataBricksProsjekt:environment:ci" } | ConvertTo-Json -Compress)

# Read the infrastructure (plan only, never apply from CI in this step):
az role assignment create --assignee $APP --role Reader --scope "/subscriptions/$SUB/resourceGroups/rg-dbxprosjekt-dev"
az role assignment create --assignee $APP --role Reader --scope "/subscriptions/$SUB/resourceGroups/rg-tfstate"
# State: plan takes a blob lease (lock), so it needs write on the state container:
az role assignment create --assignee $APP --role "Storage Blob Data Contributor" `
  --scope "/subscriptions/$SUB/resourceGroups/rg-tfstate/providers/Microsoft.Storage/storageAccounts/sttfstatech4821/blobServices/default/containers/tfstate"
# Databricks: Contributor on the workspace resource only = workspace admin, nothing else in Azure:
az role assignment create --assignee $APP --role Contributor --scope "<workspace_resource_id from terraform output>"
```

- The PowerShell JSON quoting for `--parameters` is fiddly. If it fails, write the JSON to a file and pass `@file.json`.
- **Check:** create a *temporary* client secret, run `az login --service-principal ...` locally, and run
  `terraform plan` in both modules. Whatever fails to refresh tells you which grant is missing.
  **Result (done 2026-11-16):** the grants that made the plan clean are in `infra/02-databricks/ci.tf`:
  `READ_FILES` on the storage credential and the external location (`BROWSE` isn't enough to read an external
  location), `USE_CATALOG`/`BROWSE`/`CREATE_SCHEMA` on the catalog, `USE_SCHEMA` on every schema, and
  `SELECT`/`READ_VOLUME` on bronze. The Git folder path also had to stop depending on the caller
  (`/Shared/DataBricksProsjekt`, written without `/Workspace`, the way Databricks stores it). Typical misses:
  Unity Catalog objects (catalog, schemas, storage credential, external location). Workspace admin is **not** a UC
  privilege. Add a `databricks_grants` for the CI principal in `02-databricks` (`USE_CATALOG`, `BROWSE`,
  `CREATE_SCHEMA`, `USE_SCHEMA`/`SELECT` on `bronze`). You own these objects, so the workspace provider can grant
  this without an account admin. Delete the temporary secret afterwards (`az ad app credential delete`).
- GitHub: add **variables** (not secrets, they aren't secret) `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`,
  `AZURE_SUBSCRIPTION_ID`, `DATABRICKS_HOST`, `DATABRICKS_HTTP_PATH`.

### 2.2 Tier B: workspace-level Databricks service principal

Workspace → *Settings → Identity and access → Service principals → Add → Add new*. Name it `sp-ci`, then
*Secrets → Generate secret*. Put `DATABRICKS_CLIENT_ID` / `DATABRICKS_CLIENT_SECRET` as GitHub **secrets** in an
environment `ci` (section 7.6). Grant it UC privileges with `databricks_grants` in Terraform (same list as in 2.1).
- **Check:** if "Add new" isn't offered, or the secret can't be created, account-level restrictions apply. Use tier C.
- **Check:** whether `databricks_service_principal` + `databricks_service_principal_secret` work with the
  *workspace* provider in your provider version. If they do, define `sp-ci` in Terraform instead of by hand.
  The secret then ends up in Terraform state (Entra-only storage, acceptable for a demo).

### 2.3 Tier C: PAT

User settings → *Developer → Access tokens*, lifetime **30 days**, comment `github-ci`. GitHub secret
`DATABRICKS_TOKEN` in environment `ci`. Put a calendar reminder for the expiry. Say in the interview why this is the
weakest option: it's long-lived, it's a person's identity, and it has all of your privileges.

## 3. The job: `regnskap-daily`

### 3.1 Shape

```
regnskap-daily  (git_source: github.com/Helland97/DataBricksProsjekt @ main, schedule 06:00 Europe/Oslo)
│
├─ ingest        spark_python_task  ingestion/jobs/daily_load.py   env "ingest"   retries 1
│                fake API in a thread -> dlt -> lakehouse_dev.bronze, then a bronze-vs-source check
│
└─ dbt_build     dbt_task  (depends_on: ingest)                    env "dbt"      warehouse wh-dbxprosjekt
                 dbt deps
                 dbt source freshness
                 dbt build --exclude-resource-type unit_test
```

- **Why two tasks and not one script:** each task gets its own retries, timeout, logs and repair. If dbt fails,
  *Repair run* reruns only `dbt_build` without loading again. That only works if `ingest` is idempotent, and it is:
  merge on keys plus dlt state.
- **Why `dbt build` and not `run` then `test`:** `build` runs in DAG order and tests each model before its children
  use it. A failing `error` test on a staging model stops gold from being rebuilt on bad data.
- **Why exclude unit tests in the job:** unit tests check SQL logic against fixed input. They say nothing about
  today's data, so they belong in CI (section 7.3). Data tests (including the `audit` controls) stay in the job.
- **Freshness** after ingest checks that the load actually arrived. With `warn_after` it only warns. Leave it that
  way for now. Add `error_after: {count: 36, period: hour}` once the schedule is running.

### 3.2 Terraform: `infra/02-databricks/jobs.tf`

Move the job out of `main.tf` into its own file, and rename it with a `moved` block so Terraform **updates** the
existing job (same job id and run history) instead of destroying and recreating it:

```hcl
moved {
  from = databricks_job.dbt
  to   = databricks_job.daily
}

locals {
  # Pinned to the same versions as the uv.lock files. ci/check_pins.py fails the PR if they drift (section 7.2).
  ingest_dependencies = [
    "dlt[databricks,parquet]==<from ingestion/uv.lock>",
    "faker==<...>",
    "fastapi==<...>",
    "uvicorn==<...>",
  ]
  dbt_dependencies = [
    "dbt-core==<from dbt/uv.lock>",
    "dbt-databricks==<...>",
  ]
}

resource "databricks_job" "daily" {
  name                = "regnskap-daily"
  description         = "dlt -> bronze, then dbt build (silver/gold + data tests). Code from Git: ${var.git_branch}."
  max_concurrent_runs = 1        # two runs at once would merge into the same tables
  timeout_seconds     = 3600

  queue { enabled = true }      # a manual run during the scheduled one waits instead of being skipped

  git_source {
    url      = var.git_repo_url
    provider = "gitHub"
    branch   = var.git_branch
  }

  parameter {
    name    = "sim_day"
    default = "auto"            # see section 4.2. Override in "Run now with different parameters"
  }

  environment {
    environment_key = "ingest"
    spec {
      client       = "3"        # Check: needs Python >= 3.12 (ingestion/pyproject.toml). Pick the version that has it
      dependencies = local.ingest_dependencies
    }
  }

  environment {
    environment_key = "dbt"
    spec {
      client       = "3"
      dependencies = local.dbt_dependencies
    }
  }

  task {
    task_key                  = "ingest"
    environment_key           = "ingest"
    max_retries               = 1
    min_retry_interval_millis = 60000
    timeout_seconds           = 1800

    spark_python_task {
      source      = "GIT"
      python_file = "ingestion/jobs/daily_load.py"
      parameters = [
        "--day", "{{job.parameters.sim_day}}",
        "--run-date", "{{job.start_time.iso_date}}",
        "--server-hostname", trimprefix(local.azure.workspace_url, "https://"),
        "--http-path", databricks_sql_endpoint.this.odbc_params[0].path,
      ]
    }
  }

  task {
    task_key        = "dbt_build"
    environment_key = "dbt"
    depends_on { task_key = "ingest" }

    dbt_task {
      source            = "GIT"
      project_directory = "dbt"
      commands = [
        "dbt deps",
        "dbt source freshness",
        "dbt build --exclude-resource-type unit_test",
      ]
      warehouse_id = databricks_sql_endpoint.this.id
      catalog      = databricks_catalog.this.name
      schema       = "silver"
    }
  }

  schedule {
    quartz_cron_expression = "0 0 6 * * ?"
    timezone_id            = "Europe/Oslo"
    pause_status           = var.job_schedule_paused ? "PAUSED" : "UNPAUSED"
  }

  email_notifications {
    on_failure                = var.alert_emails
    no_alert_for_skipped_runs = true
  }

  health {
    rules {
      metric = "RUN_DURATION_SECONDS"
      op     = "GREATER_THAN"
      value  = 1800             # normally a few minutes; half an hour means something hangs
    }
  }
}
```

- New variable `alert_emails` (`list(string)`, default `[]`). Put your address in `terraform.tfvars` (gitignored),
  not in the code. The repo is public.
- Rename the output `dbt_job_url` → `job_url`.
- **Check** the exact attribute names against your provider version (`databricks/databricks ~> 1.0`):
  `parameter`, `queue`, `health`, and dynamic value references like `{{job.start_time.iso_date}}`.
- **Check** that `spark_python_task` with `source = "GIT"` runs on serverless with an `environment_key`. If not,
  use a `python_wheel_task` or a notebook task that calls the same `main()`.

### 3.3 "What's on the right branch is what runs"

- Every run does a fresh checkout of `var.git_branch`. Nothing is copied into the workspace. The run page shows the
  **commit SHA** it ran. That's your audit trail from data back to code.
- What makes this safe is the **branch protection** on `main` (section 7.7). Nothing reaches `main` without a green
  PR, so nothing untested reaches the job.
- Alternatives you should be able to compare:
  - `git_source { tag = "v1.4.0" }` or `commit = "..."`: pin prod to a release. More control, but every release
    needs a Terraform change (or a CI step that moves the tag).
  - A `release` branch for prod and `main` for dev: two jobs, same code, different `git_branch`.
  - **Databricks Asset Bundles (DABs):** the job is defined in YAML in the repo, and CI runs
    `databricks bundle deploy`, which uploads a *snapshot* of the code. Deployment is explicit, there's
    dev/prod targets, and code and job definition change in the same PR. The cost is that CI needs deploy
    credentials. **Choice here: Terraform + `git_source`**, because the job already lives in Terraform next to the
    warehouse and catalog it uses, and because the requirement is "Git as the source". Say that DABs is what you'd
    look at next, especially if a team wants to change jobs without touching infrastructure code.

### 3.4 Optional: `run_as` a workspace-level service principal

If tier B works (section 2.2), you can create a second SP, `sp-job`, the same way and set
`run_as { service_principal_name = <its application id> }`. Then grant it the pipeline privileges on the schemas
with `databricks_grants`. Watch the ownership trap from step 4, section 3: you own every table today, and an SP
can't `create or replace` a table it doesn't own. Either transfer ownership of the schemas and tables to `sp-job`,
or skip `run_as` for now. **Recommendation: skip it in this step** and list it under known compromises. This step is
about orchestration and CI, and it shouldn't stall on identity again.

## 4. The ingest task: `ingestion/jobs/daily_load.py`

### 4.1 The problem: the source is a fake API on your laptop

In the job, there is no `uvicorn` running and no `ingestion/data/`. The task has to bring its own source:

1. Generate the data into a temp folder with the same seed (deterministic, so it's the same data every run).
2. Start the fake API in a background thread on `127.0.0.1` and a free port.
3. Run `run_days()` against it, then the bronze-vs-source comparison, then stop the server.

**Don't copy the server code from the test.** Move the "start uvicorn in a thread, wait until the port answers"
logic from `tests/test_pipeline.py` into `fake_api/serve.py` (a context manager, `with serve(data_dir) as url:`),
and use it from both the test and the job. A shared helper means the test exercises the same startup the job uses.

```python
# ingestion/jobs/daily_load.py (sketch)
def main() -> None:
    args = parse_args()          # --day auto|N, --run-date YYYY-MM-DD, --server-hostname, --http-path
    os.chdir(INGESTION_DIR)      # dlt reads .dlt/config.toml from the current directory
    configure_databricks(args)   # section 4.3
    day = resolve_day(args.day, args.run_date)

    with tempfile.TemporaryDirectory() as tmp:
        write_dataset(Path(tmp), seed=42, days=SIM_DAYS)          # generator + mess, as in the test fixture
        with serve(Path(tmp)) as api_url:
            pipeline = dlt.pipeline(
                pipeline_name="regnskap_databricks",               # same name as local runs: same state
                destination=destination("databricks"),
                dataset_name="bronze",
                pipelines_dir=f"{tmp}/pipelines",                  # don't rely on ~/.dlt on serverless
            )
            run_days(pipeline, api_url, [day])
            check_bronze(compare(pipeline, api_url))               # raises -> task fails
```

- `export_schema_path` is left out in the job. The checkout is thrown away after the run, so writing YAML there is
  pointless. Make it an argument in `regnskap.py` instead of always set.
- `pipeline_name="regnskap_databricks"` is the same as `--destination databricks` locally. Local runs and the job
  then share one dlt state in `bronze._dlt_pipeline_state`. That's what you want: one bronze, one cursor. But don't
  run `replay.ps1` while the schedule is on (section 6).
- **Check:** whether `__file__` is set in a `spark_python_task` from Git. If it isn't, pass the repo path as an
  argument, or locate `ingestion/` from `os.getcwd()`.

### 4.2 Which simulated day does a scheduled run load?

The fake API has a clock (day 1–30, by arrival day). A real source just has "now". Map the run date to a simulated
day:

- `--day auto`: `day = (run_date - SIM_ANCHOR).days + 1`, clamped to `1..SIM_DAYS`. `SIM_ANCHOR` is the date the
  schedule was turned on (a constant in the script, or a second job parameter `sim_anchor`).
- `--day 7`: load exactly day 7 (manual runs, demos, backfills).
- After day 30 the clock stays on day 30. Every run then loads nothing new, the comparison still passes, and dbt
  rebuilds the same numbers. That's a nice live proof of **idempotency**: you can show the run history and say
  "nothing changed, and nothing should have".
- If you'd rather have more days, generate with `--days 90`. Check first that the mess steps (schema change on day
  15, closed periods in the seed) still make sense.

### 4.3 Authentication inside Databricks

- In `databricks_setup.py`, **don't** set `DATABRICKS_AUTH_TYPE=azure-cli` when running in Databricks. Detect it with
  `os.environ.get("DATABRICKS_RUNTIME_VERSION")`. On Databricks, the SDK's default auth picks up the job's own
  credentials, so the job writes as its run-as identity (you, for now).
- `configure_databricks()` sets `DESTINATION__DATABRICKS__CREDENTIALS__SERVER_HOSTNAME` and `..._HTTP_PATH` from the
  task parameters. dlt reads config from environment variables, and `secrets.toml` doesn't exist in the job.
- **Check:** whether dlt's Databricks destination picks up the runtime's default credentials on serverless (recent
  dlt versions do, through `WorkspaceClient()`). If not, the fallback is an OAuth secret for a workspace SP in a
  **Databricks secret scope**, read with `dbutils.secrets.get` and passed in as `client_id`/`client_secret`. Never
  pass secrets as plain task parameters: they show up in the run page.

### 4.4 Make the task fail for the right reasons

`check_bronze()` turns the comparison table into a contract: after a load, `missing`, `duplicates` and `stale` must
be 0 for every table, otherwise `raise SystemExit(...)` with the table printed. A job that "succeeds" with missing rows
is worse than one that fails. This is the same check you ran by eye in step 2, now automated.

- `ContractViolation` (schema contract) must also fail the task. Today `main()` catches it and prints `STOPPED`.
  In the job script, let it raise.
- Add a pytest for `resolve_day()` (anchor, clamp, explicit day) and for `check_bronze()` (passes on zeros, fails on
  a missing row). These are pure functions and the cheapest tests in the repo.

## 5. The dbt task

- **Pin the versions** in `local.dbt_dependencies` to exactly what `dbt/uv.lock` has. Today the job allows
  `>=1.9,<2.0` while local runs `>=1.10`. A new adapter release could change behaviour in the job only, and that's
  the hardest kind of bug to find.
- The `dbt_task` writes its own `profiles.yml` from `warehouse_id`, `catalog` and `schema`. Don't commit one.
- `snapshot_time` var is `null` in the job, so snapshots use `current_timestamp()`. That's correct for scheduled runs.
  `replay.ps1` stays a local tool.
- **Check:** `dbt build --exclude-resource-type unit_test` needs dbt ≥ 1.8. Fine with 1.10.
- Keep the dbt artifacts: after a failure, the run page has the dbt logs. If you want `run_results.json` too, add
  `dbt docs generate` as a last command, or look at what the `dbt_task` offers for artifacts.

## 6. Turning it on

1. Merge the code (job script, `jobs.tf`, `databricks_setup.py` change) through a PR with green CI. The job only
   sees `main`.
2. `terraform apply` in `02-databricks` (locally, with `job_schedule_paused = true`). Check the plan says
   **update in-place** for the job, not destroy/create (the `moved` block).
3. Reset to a known state: `uv run python -m pipelines.regnskap --day 1 --destination databricks --refresh`, then
   `dbt run-operation reset_snapshots`.
4. *Run now* with `sim_day = 2`. Check both tasks, the commit SHA on the run page, and row counts in gold.
5. Run it again with `sim_day = 2`. Nothing should change (idempotency).
6. Set `SIM_ANCHOR` to tomorrow, `job_schedule_paused = false`, apply. From now on, don't load by hand. Every load
   goes through the job.
7. **Cost:** a daily run is a few minutes of serverless compute plus the warehouse (auto-stop 10 min). Pause the
   schedule when you're not using the project.

```
    ci.yml               # every PR (also from forks): lint, tests, terraform validate, dbt parse. No secrets
    dbt-pr.yml           # PRs from this repo only: dbt build into pr_<n>_* schemas
    terraform-plan.yml   # tier A only: terraform plan for both modules, posted as a PR comment
    pr-cleanup.yml       # PR closed: drop the pr_<n>_* schemas
  dependabot.yml         # weekly updates for github-actions (and pip/terraform if you want)
.pre-commit-config.yaml  # the same linters locally, so CI never surprises you
.sqlfluff                # SQL lint config (dbt/)
ruff.toml                # Python lint/format config (repo root, covers ingestion/ and ci/)
.tflint.hcl              # tflint with the azurerm ruleset
dbt/profiles.ci.yml      # committed, only env_var() lookups, no values
dbt/macros/drop_pr_schemas.sql
ci/check_pins.py         # job pins in jobs.tf == uv.lock versions
```

### 7.2 `ci.yml`: fast checks without credentials

Runs on `pull_request` and on `push` to `main`. Top-level `permissions: contents: read`. Jobs run in parallel:

| Job | Steps |
|---|---|
| `python` | `astral-sh/setup-uv`, `uv sync --directory ingestion`, `ruff check`, `ruff format --check`, `uv run --directory ingestion pytest`. The pipeline tests run on DuckDB with the fake API, so they need no secrets |
| `sql-lint` | `sqlfluff lint dbt/models dbt/tests dbt/macros`. Use the **jinja templater** with `apply_dbt_builtins = True`, not the dbt templater. The dbt templater needs a working profile, which forks don't have |
| `dbt-parse` | `dbt deps` + `dbt parse` with `profiles.ci.yml` and dummy env values. Catches broken `ref()`s, YAML errors and bad Jinja without a warehouse. **Check** that `dbt-databricks` parses without connecting |
| `terraform` | `terraform fmt -check -recursive infra`, then per module `terraform init -backend=false` + `terraform validate`, then `tflint --recursive` |
| `pins` | `python ci/check_pins.py`: read the pinned versions in `jobs.tf` and compare with `ingestion/uv.lock` and `dbt/uv.lock` |
| **`ci-ok`** | `needs: [all of the above]`, `if: always()`, fails if any needed job failed. **This is the only required check** |

- **Why one aggregator job:** with path filters (`on.pull_request.paths`), a workflow that doesn't trigger never
  reports, and a required check that never reports blocks the merge forever. Run the workflow on every PR, skip jobs
  inside it with `dorny/paths-filter` + `if:`, and make `ci-ok` the one required check. A skipped job counts as
  success, a failed one doesn't.
- `sqlfluff`: start with `dialect = databricks`, a small rule set (layout, capitalisation, aliasing) and
  `max_line_length = 120`. Run `sqlfluff fix` once locally in its own PR, so the "format everything" diff isn't
  mixed with real changes.
- Cache: `setup-uv` with `enable-cache: true`, and the `.terraform` plugin cache. Keep the workflow under ~3 minutes.

### 7.3 `dbt-pr.yml`: build every PR in its own schemas

```yaml
on:
  pull_request:
    paths: ["dbt/**", ".github/workflows/dbt-pr.yml"]
concurrency:
  group: dbt-pr-${{ github.event.pull_request.number }}
  cancel-in-progress: true            # a new push cancels the old build
permissions:
  contents: read
  id-token: write                     # tier A only
jobs:
  build:
    if: github.event.pull_request.head.repo.full_name == github.repository   # never for forks
    environment: ci
    runs-on: ubuntu-latest
    env:
      DBT_SCHEMA_PREFIX: pr_${{ github.event.pull_request.number }}_
      DBT_PROFILES_DIR: ${{ github.workspace }}/dbt
      DATABRICKS_HOST: ${{ vars.DATABRICKS_HOST }}
      DATABRICKS_HTTP_PATH: ${{ vars.DATABRICKS_HTTP_PATH }}
      # tier B: DATABRICKS_CLIENT_ID/SECRET from secrets. tier C: DATABRICKS_TOKEN from secrets.
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v6
      # tier A only: azure/login@v2 with client-id/tenant-id/subscription-id (OIDC), then auth_type azure-cli
      - run: uv run --directory dbt dbt deps
      - run: uv run --directory dbt dbt build --target ci     # includes unit tests
      - if: always()
        uses: actions/upload-artifact@v4
        with: { name: dbt-target, path: "dbt/target/*.json" }
```

**Redirect every schema with one macro change** (`dbt/macros/generate_schema_name.sql`):

```jinja
{% macro generate_schema_name(custom_schema_name, node) -%}
    {%- set base = target.schema if custom_schema_name is none else custom_schema_name | trim -%}
    {{ env_var('DBT_SCHEMA_PREFIX', '') ~ base }}
{%- endmacro %}
```

- Locally and in the job, the prefix is empty, so nothing changes: `silver`, `gold`, `audit`. In CI, PR 12 builds into
  `pr_12_silver`, `pr_12_gold`, `pr_12_audit`.
- **Sources aren't affected.** `_erp__sources.yml` says `schema: bronze` and doesn't go through
  `generate_schema_name`. So PRs read **real bronze** and write only to their own schemas. That's the point: real
  data, no side effects on prod.
- Use an env var rather than `target.name`. The job's `dbt_task` generates its own profile and you don't control its
  target name. An env var works the same everywhere.
- Fix `reset_snapshots.sql`: use `generate_schema_name('silver', none)` instead of the literal `'silver'`, so it never
  touches prod snapshots from a PR.
- `profiles.ci.yml` (committed, target `ci`): `host: "{{ env_var('DATABRICKS_HOST') }}"`, `http_path`,
  `catalog: lakehouse_dev`, `schema: silver`, and the `auth_type` for your tier (`oauth` with
  `client_id`/`client_secret` from `env_var`, or `token: "{{ env_var('DATABRICKS_TOKEN') }}"`). **Check** that the
  CI file doesn't collide with your local `profiles.yml` (it's gitignored, and `DBT_PROFILES_DIR` decides which one
  is read). Name it `profiles.yml` inside a `dbt/ci/` folder if dbt insists on the file name.
- Full build per PR is fine: the data is small and the warehouse is serverless. **Stretch: Slim CI.** On push to
  `main`, run `dbt parse` and upload `manifest.json` as an artifact. In the PR, download it and run
  `dbt build --select state:modified+ --defer --state prod-manifest/`. Only changed models and their children are
  built, and unchanged parents are read from prod. Explain the trade-off: faster and cheaper, but `--defer` reads
  prod tables, so the PR result depends on prod being healthy.
- Write a short **job summary** (`$GITHUB_STEP_SUMMARY`) from `run_results.json`: models built, tests passed, warned,
  failed, with the failing test names. Reviewers shouldn't have to open logs.

### 7.4 `pr-cleanup.yml`: drop PR schemas when the PR closes

`on: pull_request: types: [closed]`, same identity, runs
`dbt run-operation drop_pr_schemas --args "{prefix: pr_12_}"`.

```jinja
{% macro drop_pr_schemas(prefix) %}
    {#- Guard: never drop anything that isn't a PR schema. An empty prefix would match every schema. -#}
    {% if not modules.re.fullmatch('pr_[0-9]+_', prefix) %}
        {{ exceptions.raise_compiler_error("refusing to drop schemas for prefix '" ~ prefix ~ "'") }}
    {% endif %}
    {% set schemas = run_query("show schemas in " ~ target.database ~ " like '" ~ prefix ~ "*'") %}
    {% for row in schemas %}
        {% do run_query("drop schema if exists " ~ target.database ~ "." ~ row[0] ~ " cascade") %}
        {% do log("dropped " ~ row[0], info=true) %}
    {% endfor %}
{% endmacro %}
```

- The regex guard is the important part. Cleanup code that takes a prefix is one empty string away from
  `drop schema silver cascade`. Add a weekly scheduled run of the same workflow that drops `pr_*` schemas for PRs that
  are no longer open, in case a cleanup run failed.

### 7.5 `terraform-plan.yml` (tier A)

- Trigger: `pull_request` with `paths: ["infra/**"]`, same-repo only, `permissions: id-token: write`,
  `pull-requests: write`.
- Env: `ARM_USE_OIDC=true`, `ARM_CLIENT_ID`, `ARM_TENANT_ID`, `ARM_SUBSCRIPTION_ID` from `vars`. `TF_VAR_subscription_id`
  for `01-azure`, since `*.tfvars` are gitignored. The Databricks provider uses the same ARM_* login through
  `azure_workspace_resource_id`.
- Steps per module (matrix `[01-azure, 02-databricks]`, `max-parallel: 1`, because 02 reads 01's state):
  `terraform init`, `terraform plan -input=false -lock-timeout=5m -no-color -out=tfplan`, then
  `terraform show -no-color tfplan` into a **sticky PR comment** (one comment that's updated on each push, not a new
  one per push). Fail the job only on plan errors, not on "changes present".
- **No `apply` from CI in this step.** Apply stays local, by you, after merge. The next maturity step would be
  `apply` on push to `main` behind a GitHub environment with required reviewers, from the saved plan file. Be ready
  to explain why you stopped short: CI applying infrastructure needs write credentials, state locking discipline and
  a rollback story. That's a deliberate decision, not a gap you didn't notice.
- Without tier A, this workflow doesn't exist. `ci.yml` still runs `fmt`/`validate`/`tflint`, and the PR description
  template has a checkbox: *"Ran `terraform plan` locally, output pasted below"*.

### 7.6 Secrets and permissions in CI

- **Never use `pull_request_target`** for anything that checks out PR code. It runs with secrets on code from forks.
  `pull_request` doesn't give secrets to forks, which is what you want for a public repo.
- Secrets (tier B/C) live in a GitHub **environment** `ci`, not as repository secrets, so only jobs that declare
  `environment: ci` can read them. Don't add a branch restriction to the environment: PR builds run from feature
  branches, which a "selected branches" rule would block. The protection is that forks get no secrets on
  `pull_request`, and that only the jobs that declare `environment: ci` can read them.
- Every workflow sets `permissions:` explicitly. Default `contents: read`. Only what's needed on top
  (`id-token: write` for OIDC, `pull-requests: write` for the plan comment).
- Pin third-party actions (`dorny/paths-filter`, the comment action) to a **commit SHA**, not a tag. Tags can be
  moved. First-party `actions/*` on a major version is common practice. Dependabot keeps both up to date.

### 7.7 Branch protection on `main`

Settings → Branches (or Rulesets): require a PR, require status checks **`ci-ok`** and **`dbt-pr / build`** (plus
`terraform-plan` in tier A, if you make it required), require branches to be up to date, block force pushes and
deletion. As the only developer you can't approve your own PR, so don't require reviews. CI is the reviewer.
This rule is what turns "the job runs whatever is on `main`" into "the job runs only tested code".

1. Branch `feature/break-trial-balance`. Change `rpt_trial_balance.sql` so one account's sign is flipped.
2. Open a PR. `ci.yml` goes green (it's valid SQL). `dbt-pr.yml` goes **red**:
   `assert_trial_balance_nets_to_zero` fails in `pr_<n>_audit`. Show the job summary and the failing rows in
   `lakehouse_dev.pr_<n>_audit`.
3. The merge button is blocked by branch protection.
4. Fix it, push. Green. Merge. `pr-cleanup.yml` drops `pr_<n>_*`.
5. Next morning (or *Run now*): the job checks out the new `main` commit. The run page shows that SHA. Gold is

6. Also show a red **job** run. Add a job parameter `contract` (default `evolve`) that is passed on to `run_days()`.
   Run with `sim_day = 15` and `contract = freeze-types`. The ingest task fails on the day 15 schema change, the
   failure email arrives, and `dbt_build` never starts. Then run again with `contract = evolve` (or use *Repair run*).

## 9. Things to be able to explain

- **Orchestration in Databricks vs. outside it** (Airflow, ADF): Workflows is the natural choice when everything runs
  in Databricks. No extra infrastructure, lineage and run history in the same place, serverless compute per task.
  Airflow pays off when you orchestrate across many systems. The empty `orchestration/` folder can hold a local
  Airflow DAG as a bonus, calling the same job with `DatabricksRunNowOperator`. Then Airflow only triggers it, and the
  logic stays in one place.
- **Git source vs. deploy (DABs)**, section 3.3.
- **Idempotency and repair:** merge on keys + dlt state + `dbt build` = rerunnable. Why that matters for retries.
- **Where tests run:** unit tests and lint in CI (logic), data tests in the job (data), freshness after load
  (arrival), bronze-vs-source check in ingest (completeness). Four layers, each catches something different.
- **PR isolation:** schema prefix per PR, sources from real bronze, guarded cleanup. Slim CI and `--defer` as the
  next step.
- **Secretless CI with OIDC** vs. client secret vs. PAT (section 2). Why `pull_request_target` is dangerous.
- **Version pinning:** job, local and CI on the same versions, enforced by `check_pins.py`. "Works on my machine"
  is a missing pin.
- **The `moved` block:** refactoring Terraform without destroying resources, same as a rename refactor in code.

## 11. Known compromises (write them in the README)

- The job runs as **you**, not a service principal (step 4 blocked). Planned fix: `run_as` + ownership transfer.
- Tier B/C: CI has a long-lived secret. Tier C: CI has *your* privileges.
- PR builds read unmasked bronze. Fine for synthetic data, not for real personal data. With step 4 in place, the CI
  identity would be in a group without access to raw PII.
- `terraform apply` is manual. Plan in CI (tier A) or locally.
- The fake API runs inside the ingest task. A real source would be an external system with its own credentials in a
  secret scope. The job shape stays the same.

## 12. Cleanup

- Pause the schedule (`job_schedule_paused = true`) when you're not working on the project.
- `terraform destroy` removes the job together with the rest. Drop leftover `pr_*` schemas first (the cleanup
  workflow, or `drop_pr_schemas` by hand), otherwise destroying the catalog fails on non-empty schemas.
- Tier A: `az ad app delete --id $APP` removes the app, the federated credentials and the role assignments go with
  it (check role assignments with `az role assignment list --assignee $APP` first). Tier B: delete `sp-ci` in the
  workspace. Tier C: revoke the PAT.
